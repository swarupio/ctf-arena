## Dark hover contrast
- Owner report (screen recording, dark mode): a hovered navbar link and a hovered challenge card went black on the dark surface. Root cause: `styles.css` has a global `a:hover { background: var(--color-accent); color: var(--color-on-accent) }`. Components that are anchors and replaced only the hover background (surface, tint, transparent) kept the dark on-accent text. On white (light) that is black on white and looks right; on a dark surface it is unreadable.
- Fix, one rule per offender, always an explicit hover `color` whose light value equals what rendered before (`--color-ink` and `--color-on-accent` are both `#0a0a0a` in light; `--color-on-accent-muted` equals light `--color-muted`): navbar links (`.site-header nav a:hover`), brand (`.brand:hover`), `.button.secondary:hover` and `button.secondary:hover`, challenge cards and solved cards, admin sidebar links, admin stat links, debrief skill chips (`.dbf-chip`), terminal mode links (`.tm-modes a`). Child text with its own colour on a card that turns lime: Cipher Lab and Crackme rung status and meta, Web Lab card `h3`, Debrief toggle sub label, terminal mode hint (all switch to `--color-on-accent` or `--color-on-accent-muted` on hover). Files: `frontend/src/styles.css` (hover rules only), `pages/Challenge.css`, `components/{admin/admin,cipherlab/cipherlab,crackme/crackme,weblab/weblab}.css`, `debrief/debrief.css`, `terminal/terminal.css`.
- Guard: `frontend/tests/hoverColor.test.js` parses every CSS file and fails when a rule whose subject is an anchor on `:hover` sets a background without a colour (anchor classes are read from the JSX plus a short documented list; allowlist is empty). It found one offender the browser audit never reached (`.dbf-chip`, only visible in a solved debrief). THEMING.md section 4 rule 15 documents the rule.

## Auth lazy-load review

Scope: `frontend/src/auth/*`, `api/client.js`, `pages/AuthPages.jsx` after aws-amplify became an on-demand chunk (reviewed against the pre-f21a3f3 behaviour; no real Cognito login was possible).

- Stored-session check: Amplify 6.22.2 (`@aws-amplify/auth` TokenStore, `AUTH_KEY_PREFIX = 'CognitoIdentityServiceProvider'`) writes `CognitoIdentityServiceProvider.<clientId>.LastAuthUser` and `.<clientId>.<user>.{idToken,accessToken,refreshToken,clockDrift,signInDetails}` to localStorage; `hasStoredSession()` matches the `CognitoIdentityServiceProvider.` prefix, so stale or expired sessions still load amplify (it refreshes or clears them), leftover device keys after sign-out do too (harmless: one extra chunk download), and a blocked or throwing storage returns true.
- Fixed (hardening): once amplify has loaded in a page it owns the session (its storage falls back to memory when localStorage is unusable, and another tab can clear keys), so `getToken()` and the restore step now use `mayHaveSession()` = amplify loaded OR a stored key exists. Before, a page whose localStorage reads empty but whose amplify held an in-memory session would have sent API calls without a token after sign-in.
- Fixed: a failed chunk download (offline, or an old chunk removed by a new deploy) surfaced as a raw `TypeError`, which the UI showed as the generic "Unable to complete this request". The loader (`createAuthLoader(importer)` in `auth/session.js`, importer injectable for tests) now rejects with `name: 'NetworkError'` (original error in `cause`), which `authMessage` maps to "Unable to connect. Check your connection and try again." The rejection is not cached, so the next click, `preload()` or API call retries. Concurrent callers share one in-flight promise.
- Added `[auth] WARNING` to `vite build` (`vite.config.js`) when a `VITE_COGNITO_*` variable is missing at build time (before, the build was silent and the deployed site showed "Authentication is not configured"). It warns, it does not fail, because `npm run build` is also used for the harness stubs.
- Checked and unchanged: error mapping table, sign-in/MFA/confirm/reset/resend call shapes, sign-out (`TeamContext` clears the API cache when the user becomes null; Hub `signedOut` and `tokenRefresh_failure` clear user, step and email), admin role from `cognito:groups` of the ID token, `/me` profile fetch, ID token (not access token) sent as Bearer, env var names (`VITE_COGNITO_REGION`, `_USER_POOL_ID`, `_CLIENT_ID`) in `.env.example` and `DEPLOY_VERCEL.md`.
- Route guards: `loading` starts true whenever a Cognito key is stored, so a hard reload or new tab on `/range` or `/admin` with a session waits ("Restoring your session") before deciding; with nothing stored it starts false and redirects to `/login` once. Verified in Chrome over the production build: signed out on `/` requests no amplify chunk; `/login` and the redirect from `/range` request `amplifyAuth` and `amplify` (login preloads on purpose); a fake `CognitoIdentityServiceProvider.x.LastAuthUser` key loads them on `/`; index.html references neither chunk.
- Risks left: (1) if the chunk cannot be downloaded during session restore, the user is treated as signed out for that page view (redirect to login) although the stored session is intact; a reload restores it. (2) Signed-out tab B does not notice a sign-in done in tab A until reload (amplify is not loaded there, so no cross-tab Hub event). (3) A browser that caches a failed dynamic import for the page lifetime would need a reload; the loader itself retries.
- Tests: `tests/authSession.test.js` (storage detector with fake storage, loader single flight and failure not cached, error table, load failure message), `tests/amplifyLazy.test.js` (only `amplify.js` and `amplifyAuth.js` import aws-amplify, the static graph from `main.jsx` never reaches them, `session.js` is the only dynamic importer).
- Manual with a real login (owner): see the final report of this review.
